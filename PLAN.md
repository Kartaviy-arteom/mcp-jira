# План расширения Jira MCP

## 1. Расширение `get-jira-issue`

Сохранить существующие поля:

- `id`
- `key`
- `summary`
- `description`
- `status`

`description` возвращается как строка или явный `null`, если описание отсутствует в Jira.

Добавить поля:

- `issueType` — тип задачи;
- `parent` — ключ и название родительской задачи;
- `subtasks` — ключ, название и статус каждой подзадачи;
- `issueLinks` — тип связи, направление, ключ, название и статус связанной задачи;
- `fixVersions` — идентификатор, название и признаки `released` и `archived`;
- `updated` — время последнего изменения задачи.

Точная структура связанных данных:

```json
{
  "parent": {
    "key": "OMSAGORA-5000",
    "summary": "Родительская задача"
  },
  "subtasks": [
    {
      "key": "OMSAGORA-5001",
      "summary": "Подзадача",
      "status": "Реализация"
    }
  ],
  "issueLinks": [
    {
      "type": "Blocks",
      "direction": "outward",
      "key": "OMSAGORA-5002",
      "summary": "Связанная задача",
      "status": "Открыта"
    }
  ],
  "fixVersions": [
    {
      "id": "18136",
      "name": "release-1.2.3",
      "released": false,
      "archived": false
    }
  ]
}
```

Правила:

- `parent` возвращается как объект или `null`;
- `subtasks`, `issueLinks` и `fixVersions` всегда возвращаются как массивы, при отсутствии данных — `[]`;
- `direction` принимает только `inward` или `outward` и определяется наличием `inwardIssue` или `outwardIssue` в ответе Jira;
- `type` содержит название типа связи Jira;
- для версии возвращаются два явных boolean: `released` и `archived`, без общего поля `state`;
- внутренний Jira `id` для parent, subtasks и links не возвращается; последующее получение задачи выполняется по `key`.

Не добавлять `assignee`, `reporter`, `priority`, кастомные поля, `labels`, `components`, `resolution` и `created`.

Не добавлять фильтр полей ответа. Согласованный ответ достаточно компактный и имеет стабильную схему.

## 2. Диагностика подключения и безопасные ошибки

Добавить `diagnose-jira-connection` без входных параметров. Использовать один авторизованный запрос:

```http
GET /rest/api/2/myself
```

Ответ:

```json
{
  "configured": true,
  "credentialsFound": true,
  "reachable": true,
  "authenticationStatus": "authenticated"
}
```

Значение полей:

- `configured` — `JIRA_URL` существует и является корректным HTTP/HTTPS URL; проверяется локально;
- `credentialsFound` — в keyring найден непустой Jira-токен;
- `reachable` — настроенный сервер вернул любой HTTP-ответ. При ошибках сети, DNS, TLS, подключения или тайм-ауте возвращается `false`;
- `authenticationStatus` — результат проверки авторизации: `authenticated`, `rejected` или `unverified`.

Значения `authenticationStatus`:

- `authenticated` — токен передан, `/rest/api/2/myself` вернул `2xx`;
- `rejected` — токен передан, Jira вернула `401` или `403`;
- `unverified` — проверку нельзя завершить из-за отсутствующего URL или токена, сетевой ошибки либо ответа Jira `5xx`.

Алгоритм диагностики:

- URL и наличие токена проверяются локально и независимо;
- при некорректном URL HTTP-запрос не выполняется, `reachable: false`, `authenticationStatus: "unverified"`;
- при корректном URL `/rest/api/2/myself` вызывается даже без токена, чтобы отдельно проверить доступность Jira;
- при отсутствии токена запрос отправляется без `Authorization`, а `authenticationStatus` остается `unverified` независимо от HTTP-ответа;
- любой HTTP-ответ означает `reachable: true`;
- сетевая ошибка означает `reachable: false` и `authenticationStatus: "unverified"`;
- ответ `5xx` означает `reachable: true` и `authenticationStatus: "unverified"`.
- при наличии токена ответы `2xx` означают `authenticated`, `401` и `403` — `rejected`, остальные HTTP-статусы — `unverified`;
- при отсутствии токена `authenticationStatus` всегда равен `unverified`, независимо от HTTP-статуса.

Не возвращать данные профиля, версию Jira, задержку запроса, токен, заголовки, stack trace, полный URL запроса и исходное тело ошибки Jira.

Существующие tools должны возвращать контролируемые MCP безопасные ошибки. Согласованные коды:

- `BAD_REQUEST`
- `AUTH_ERROR`
- `ACCESS_DENIED`
- `ISSUE_NOT_FOUND`
- `RATE_LIMITED`
- `JIRA_UNAVAILABLE`
- `NETWORK_TIMEOUT`
- `RESPONSE_FORMAT_ERROR`
- `CONFIG_ERROR`
- `ATTACHMENT_NOT_FOUND`
- `ATTACHMENT_TOO_LARGE`
- `UNSUPPORTED_ATTACHMENT_TYPE`

Ошибка может содержать только `code`, заранее определенный безопасный `message` и применимый `httpStatus`. Не возвращать исходную ошибку Jira, `cause`, stack trace или тело ответа.

Соответствие ошибок:

| Условие                                   | `code`                  |                   `httpStatus` |
| ----------------------------------------- | ----------------------- | -----------------------------: |
| Jira вернула `400`                        | `BAD_REQUEST`           |                          `400` |
| Jira вернула `401`                        | `AUTH_ERROR`            |                          `401` |
| Jira вернула `403`                        | `ACCESS_DENIED`         |                          `403` |
| Jira вернула `408`                        | `NETWORK_TIMEOUT`       |                          `408` |
| Jira вернула `429`                        | `RATE_LIMITED`          |                          `429` |
| Jira вернула `5xx`                        | `JIRA_UNAVAILABLE`      |             фактический статус |
| DNS, TLS, connection refused/reset        | `JIRA_UNAVAILABLE`      |                    отсутствует |
| Локальный тайм-аут 10 секунд              | `NETWORK_TIMEOUT`       |                    отсутствует |
| Некорректный JSON или несовместимая схема | `RESPONSE_FORMAT_ERROR` | фактический статус при наличии |
| Нет или некорректен `JIRA_URL` или токен  | `CONFIG_ERROR`          |                    отсутствует |

`404` обрабатывается с учетом операции:

- чтение задачи или списка ее вложений — `ISSUE_NOT_FOUND`;
- загрузка уже выбранного вложения — `ATTACHMENT_NOT_FOUND`.

Ошибки до HTTP-запроса:

- вложение больше установленного лимита — `ATTACHMENT_TOO_LARGE`;
- MIME-тип вложения не поддерживается — `UNSUPPORTED_ATTACHMENT_TYPE`;
- неправильные аргументы tool — `BAD_REQUEST` либо стандартная ошибка входной схемы MCP Framework.

Для остальных ответов `4xx` возвращать `BAD_REQUEST` с фактическим `httpStatus`. Исходный текст Jira в `message` не использовать; безопасное сообщение выбирается MCP по `code`.

## 4. Улучшение `get-release-tasks`

Сохранить название tool и изменить входной контракт:

```json
{
  "releaseId": "18136",
  "includeDescription": false,
  "limit": 100,
  "startAt": 0
}
```

Ответ:

```json
{
  "tasks": [
    {
      "id": "334204",
      "key": "OMSAGORA-5497",
      "summary": "Название задачи",
      "status": "Реализация"
    }
  ],
  "total": 1,
  "nextStartAt": null
}
```

Требования:

- переименовать входное поле `issueKey` в `releaseId`;
- принимать только `releaseId`; старое поле `issueKey` не поддерживать;
- возвращать `status`, который сейчас запрашивается у Jira, но отбрасывается;
- не возвращать `description` по умолчанию;
- возвращать описания только при `includeDescription: true`;
- при `includeDescription: true` возвращать `description` как строку или явный `null`;
- добавить offset-пагинацию через `startAt` и `limit`;
- `startAt` должен быть целым числом `>= 0`, по умолчанию `0`;
- `limit` должен быть целым числом от 1 до 100, по умолчанию 100;
- возвращать `total` и `nextStartAt`;
- `nextStartAt` содержит следующее смещение или `null`; для пустой или последней страницы возвращать `null`;
- следующее смещение рассчитывается как `startAt + tasks.length`;
- если `total` показывает продолжение, но Jira вернула пустую страницу, возвращать `RESPONSE_FORMAT_ERROR`;
- использовать JQL только для фильтрации задач релиза: `fixVersion=<releaseId>`;
- передавать пагинацию в Jira отдельно через `startAt` и `maxResults`;
- не добавлять в JQL фиксированную сортировку без отдельной подтвержденной потребности;
- не добавлять тип задачи, метаданные релиза, приоритет и исполнителя.

## 5. История изменений задачи

Не реализовывать `get-issue-changelog`. Текущий сценарий требует только актуальное состояние задачи, которое покрывается `get-jira-issue` и новым полем `updated`.

## 6. Комментарии задачи

Не реализовывать `get-issue-comments`. Доступная история не показывает конкретной потребности, а комментарии могут добавить значительный объем нерелевантных или чувствительных данных.

## 7. Вложения задачи

Добавить два tool.

### `list-issue-attachments`

Входные параметры:

```json
{
  "issueKey": "OMSAGORA-5391"
}
```

Возвращать только метаданные вложений:

```json
{
  "attachments": [
    {
      "id": "12345",
      "filename": "image-2026-07-06.png",
      "mimeType": "image/png",
      "size": 248310,
      "supported": true
    }
  ]
}
```

### `get-issue-attachment`

Входные параметры:

```json
{
  "issueKey": "OMSAGORA-5391",
  "attachmentId": "12345"
}
```

Возвращать загруженное изображение как MCP-блок `image`, а метаданные — в `structuredContent`:

```json
{
  "content": [
    {
      "type": "image",
      "data": "<base64>",
      "mimeType": "image/png"
    }
  ],
  "structuredContent": {
    "issueKey": "OMSAGORA-5391",
    "attachmentId": "12345",
    "filename": "image-2026-07-06.png",
    "mimeType": "image/png",
    "size": 248310
  }
}
```

Требования:

- `list-issue-attachments` возвращает метаданные всех вложений задачи и ничего не скачивает;
- поле `supported` равно `true` только для `image/png`, `image/jpeg` и `image/webp`;
- неподдерживаемые вложения также присутствуют в списке с `supported: false`;
- поддерживаемые форматы: строго `image/png`, `image/jpeg` и `image/webp`;
- максимальный размер вложения — `5 * 1024 * 1024` байт (`5 242 880` байт);
- при превышении лимита возвращать `ATTACHMENT_TOO_LARGE`;
- если вложение отсутствует среди вложений указанной задачи, возвращать `ATTACHMENT_NOT_FOUND` и не выполнять загрузку;
- учитывать права токена Jira;
- не возвращать локальный путь, требующий авторизации URL Jira, публичный или временный URL, а также base64 внутри текстового JSON;
- извлекать числовой `attachmentId` из документированного URI `self` в метаданных Jira; при несовместимом URI возвращать `RESPONSE_FORMAT_ERROR`;
- загружать содержимое по документированному URI `content` из метаданных Jira только после проверки протокола, origin, базового пути Jira и принадлежности выбранному вложению;
- передавать в общий Jira-клиент только проверенный внутренний endpoint; произвольные внешние URL не разрешать;
- до загрузки проверять MIME-тип и размер из метаданных вложения; при попытке загрузить вложение с `supported: false` возвращать `UNSUPPORTED_ATTACHMENT_TYPE`;
- проверять, что `Content-Type` ответа совпадает с MIME-типом из метаданных;
- при сравнении `Content-Type` нормализовать регистр и игнорировать параметры после `;`; в результате возвращать канонический MIME-тип `image/png`, `image/jpeg` или `image/webp`;
- читать тело ответа потоком и немедленно прекращать загрузку при превышении `5 * 1024 * 1024` байт, включая случаи с отсутствующим или некорректным `Content-Length`;
- проверять фактический формат загруженных байтов по сигнатуре PNG, JPEG или WebP;
- не сохранять содержимое, base64 или бинарные данные вложения на диск и не записывать их в лог;
- при несовпадении MIME-типа или сигнатуры возвращать безопасную ошибку `RESPONSE_FORMAT_ERROR`.

## 12. Worklog

Реализовать read-only tool `get-issue-worklogs`.

Входные параметры:

```json
{
  "issueKey": "OMSAGORA-3520"
}
```

Ответ:

```json
{
  "issueKey": "OMSAGORA-3520",
  "totalTimeSeconds": 28800,
  "contributorsCount": 3,
  "worklogsCount": 5
}
```

Требования:

- `totalTimeSeconds` — сумма `timeSpentSeconds` всех доступных записей;
- `contributorsCount` — количество уникальных сотрудников;
- `worklogsCount` — количество записей worklog;
- выполнять один запрос к документированному endpoint Jira Server/Data Center 9.12.23, который возвращает все worklog задачи;
- проверять полноту ответа через `worklogs.length === total`; при расхождении возвращать `RESPONSE_FORMAT_ERROR`;
- никогда не возвращать имена, логины, account ID и другие идентификаторы сотрудников;
- не возвращать комментарии и отдельные записи worklog;
- сохранять анонимность сотрудников даже при единственном авторе;
- для подсчета уникальных сотрудников использовать только в памяти первый доступный документированный Jira Server/Data Center идентификатор автора в порядке `key`, `name`;
- при подсчете включать тип идентификатора в ключ уникальности: `key:<value>` или `name:<value>`;
- не использовать `displayName`, поскольку он не гарантирует уникальность и может изменяться;
- хранить внутренние идентификаторы только до завершения вызова, не возвращать их, не записывать в лог и не включать в сообщения ошибок;
- если хотя бы у одной записи отсутствуют `key` и `name`, не угадывать количество сотрудников и возвращать `RESPONSE_FORMAT_ERROR`;
- не реализовывать `add-issue-worklog`, поскольку MCP остается read-only.

### 15.1. Общий Jira HTTP-клиент

Создать общий Jira HTTP-клиент — обертку над `fetch`.

При реализации пунктов 1–14 допускаются только минимальные изменения существующего клиента, необходимые новым tools; переработка его архитектуры не допускается.

Клиент отвечает за:

- получение и валидацию `JIRA_URL` во время выполнения запроса;
- получение Jira-токена из keyring во время выполнения запроса;
- безопасное объединение базового URL, относительного пути и query-параметров;
- добавление заголовков `Authorization` и `Accept`;
- выполнение запроса с единым тайм-аутом 10 секунд;
- фактическую отмену запроса через `AbortSignal.timeout(10_000)`, без использования `Promise.race`;
- чтение HTTP-статуса;
- преобразование сетевых и HTTP-ошибок в согласованные внутренние ошибки;
- безопасное чтение и разбор JSON-ответов;
- предоставление потокового чтения бинарного ответа для `get-issue-attachment` без попытки разобрать его как JSON.

Каждый tool самостоятельно определяет Jira endpoint и передает клиенту:

- относительный `pathname` без начального `/`;
- query-параметры;
- Zod-схему ожидаемого ответа Jira для JSON-запросов.

Пример:

```ts
jiraClient.getJson({
  pathname: `rest/api/2/issue/${encodeURIComponent(issueKey)}`,
  query: {
    fields: "summary,status,description",
  },
  schema: jiraIssueSchema,
});
```

Клиент не должен знать endpoints и бизнес-схемы конкретных tools. Он проверяет, что `pathname` является относительным, нормализует завершающий `/` у `JIRA_URL`, строит URL через `URL`, а query — через `URLSearchParams`.

Для контекстной обработки `404` конкретный tool передает клиенту безопасный код, например `notFoundCode: "ISSUE_NOT_FOUND"` или `notFoundCode: "ATTACHMENT_NOT_FOUND"`.

Динамические сегменты пути кодируются вызывающим tool через `encodeURIComponent`. Преобразование Jira-ответа в выходную модель MCP остается ответственностью конкретного tool.

Не загружать URL и токен на уровне модуля: это необходимо, чтобы `diagnose-jira-connection` мог корректно сообщить об отсутствующей конфигурации или учетных данных без падения MCP при запуске.

### 15.2. Валидация динамических параметров и JQL

Построение URL и query выполняется только через механизм общего Jira HTTP-клиента из пункта 15.1.

Дополнительные требования:

- не принимать raw JQL ни в одном tool;
- проверять каждый динамический параметр предметной Zod-схемой до формирования запроса;
- разрешать для `releaseId` только строковый числовой идентификатор по шаблону `^\d+$`;
- нормализовать `issueKey` через `trim()` и `toUpperCase()`;
- проверять ключи Jira-задач по шаблону `^[A-Z][A-Z0-9_]*-\d+$`;
- дополнительно кодировать проверенные динамические сегменты пути через `encodeURIComponent`;
- не пересылать в Jira неизвестные пользовательские query-параметры.

Под raw JQL понимается произвольное JQL-выражение, полностью или частично переданное вызывающей стороной, например:

```json
{
  "jql": "fixVersion = 18136 OR project = OTHER ORDER BY updated DESC"
}
```

Tools не должны предоставлять параметр `jql`, принимать отдельные фрагменты условий или дописывать пользовательский текст в JQL. Разрешен только JQL, который MCP формирует самостоятельно по фиксированному шаблону из отдельных предварительно проверенных параметров.

Допустимый вход:

```json
{
  "releaseId": "18136"
}
```

На его основе MCP сам формирует строго заданное выражение `fixVersion=18136`. Вызывающая сторона не может изменить оператор, добавить условие, сортировку или обратиться к другому полю Jira.

`URLSearchParams` защищает структуру URL, но не семантику JQL. Поэтому JQL для `get-release-tasks` формируется MCP только из предварительно проверенного `releaseId`:

```ts
const releaseIdSchema = z.string().regex(/^\d+$/);
const jql = `fixVersion=${releaseId}`;
```

Схема ключа задачи:

```ts
const issueKeySchema = z
  .string()
  .trim()
  .toUpperCase()
  .regex(/^[A-Z][A-Z0-9_]*-\d+$/);
```

Во всех tools поле `issueKey` означает ключ Jira-задачи и проверяется через `issueKeySchema`. `get-release-tasks` не принимает `issueKey` и использует только `releaseId`.

### 15.3. Единый тайм-аут запросов

Использовать для всех Jira HTTP-запросов единый фиксированный тайм-аут 10 секунд.

Требования:

- реализовать фактическую отмену запроса через `AbortSignal.timeout(10_000)`, без `Promise.race`;
- распространять тайм-аут на получение HTTP-ответа и полное чтение его тела;
- применять тот же тайм-аут к JSON-ответам и загрузке изображений размером до `5 * 1024 * 1024` байт;
- при срабатывании возвращать согласованную безопасную ошибку `NETWORK_TIMEOUT`;
- определять тайм-аут по состоянию созданного сигнала, а не считать любой `AbortError` тайм-аутом;
- не выполнять автоматические повторные запросы;
- не передавать значение тайм-аута через параметры tools;
- пока не добавлять отдельную переменную окружения для настройки тайм-аута.

Один и тот же сигнал должен использоваться как при выполнении `fetch`, так и при последующем полном или потоковом чтении тела ответа.

### 15.4. Публикация выходных схем и строгие входные схемы

Для `get-release-tasks` и всех новых JSON-tools явно подключать выходную Zod-схему к MCP Framework:

```ts
protected outputSchemaShape = outputSchema;
```

Это необходимо, чтобы tool публиковал структурированный контракт и возвращал `structuredContent`, а не только текстовый `content`.

Все входные Zod-объекты объявлять через `.strict()`:

```ts
const inputSchema = z
  .object({
    issueKey: issueKeySchema,
  })
  .strict();
```

Неизвестные входные поля должны отклоняться, а не молча удаляться. Это позволяет обнаруживать опечатки в необязательных параметрах, например `includeDescriptions` вместо `includeDescription`.

### Логирование

Пока не реализовывать отдельный сервис логирования:

- не добавлять logger и уровни логирования;
- не добавлять переменную окружения для настройки логов;
- не возвращать `errorId`, поскольку отсутствует журнал для сопоставления;
- не записывать исходные ошибки, ответы Jira и пользовательские данные в `stdout` или `stderr`;
- при разработке использовать IDE debugger и автоматические тесты;
- внутреннее исключение может сохранять исходную ошибку в `cause`, но `cause` не передается в MCP-ответ.

Вернуться к проектированию логирования после определения конкретного способа эксплуатации и потребителя production-логов.

### Автоматические тесты

Использовать Vitest как test runner.

Добавить scripts:

```json
{
  "test": "vitest run",
  "test:watch": "vitest"
}
```

Писать тесты на TypeScript без предварительной сборки `dist`. Для тестирования общего Jira HTTP-клиента предусмотреть подмену `fetch`, получения `JIRA_URL`, получения токена и внутреннего значения тайм-аута. Production-конфигурация по-прежнему использует фиксированный тайм-аут 10 секунд, недоступный через параметры tools.

Обязательное покрытие поведения:

- общий HTTP-клиент: построение URL и query, авторизация, преобразование HTTP- и сетевых ошибок, timeout, отсутствие исходной ошибки в MCP-ответе;
- `get-jira-issue`: существующие и новые поля, отсутствие родителя, пустые списки, nullable description, несовместимый ответ Jira;
- `diagnose-jira-connection`: отсутствующий URL или токен, недоступная сеть, ответы `2xx`, `401`, `403`, `5xx` и все значения `authenticationStatus`;
- `get-release-tasks`: `includeDescription`, status, отклонение старого поля `issueKey`, `startAt`, `nextStartAt` и ограничения `limit`;
- вложения: разрешенные MIME-типы, `Content-Type`, сигнатуры, оба варианта превышения размера, принадлежность задаче и формат MCP-ответа;
- `get-issue-worklogs`: проверка полного ответа, общее время, количество записей и сотрудников, отсутствие идентификаторов и комментариев в результате;
- входные схемы: нормализация и проверка `issueKey`, строгий `releaseId`, отклонение неизвестных полей и невозможность передать raw JQL;
- все согласованные безопасные коды ошибок.

Не добавлять:

- интеграционные тесты против рабочей Jira;
- snapshot-тесты;
- обязательный процент покрытия;
- тесты внутренних деталей `mcp-framework`.

Критерий достаточности: публичные контракты tools и все согласованные ветви безопасных ошибок проверены поведенческими тестами.
