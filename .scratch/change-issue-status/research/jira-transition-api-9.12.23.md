# Контракт смены статуса через Jira REST API 9.12.23

## Вывод

Статус задачи меняется не прямым обновлением поля `status`, а выполнением доступного текущему пользователю workflow transition. Минимальный безопасный сценарий состоит из чтения исходного статуса, чтения доступных переходов с метаданными полей, выбора единственного перехода по его целевому статусу, `POST` перехода и обязательного повторного чтения фактического статуса.

Источник для всех контрактов ниже — официальная [Jira Server platform REST API reference 9.12.23](https://docs.atlassian.com/software/jira/docs/api/REST/9.12.23/).

## REST-вызовы

### 1. Прочитать исходное состояние

`GET /rest/api/2/issue/{issueIdOrKey}?fields=status`

- Path-параметр принимает числовой id или ключ задачи. Jira также может найти ключ без учёта регистра или старый ключ перемещённой задачи; канонический текущий ключ возвращается в ответе.
- `fields=status` ограничивает ответ нужным полем. Успех — `200` с issue JSON; `404` означает, что задача не найдена либо пользователь не вправе её видеть.
- Из ответа нужны `key`, `fields.status.id` и `fields.status.name`.

См. [Get issue](https://docs.atlassian.com/software/jira/docs/api/REST/9.12.23/#api/2/issue-getIssue).

Если `trim()` и регистронезависимое представление текущего `status.name` совпадают с целевым именем, операция завершается без записи: `changed: false`. Это исходное чтение одновременно подтверждает фактическое состояние для no-op.

### 2. Прочитать доступные переходы

`GET /rest/api/2/issue/{issueIdOrKey}/transitions?expand=transitions.fields`

- Возвращаются только переходы, доступные для этой задачи текущему пользователю.
- `expand=transitions.fields` обязателен для получения полей transition screen, признака `required`, схемы, допустимых операций/значений и признака `hasDefaultValue`.
- Ответ `200` имеет форму `{ "transitions": [...] }`. Для выбора важны `transition.id`, `transition.name`, `transition.to.id`, `transition.to.name`, `transition.fields`.
- `404`: задача не найдена либо пользователь не вправе её видеть.

См. [Get transitions](https://docs.atlassian.com/software/jira/docs/api/REST/9.12.23/#api/2/issue-getTransitions) и схему `Transitions Meta` на той же странице.

Выбор выполняется среди переходов, у которых `transition.to.name.trim()` совпадает с целевым статусом без учёта регистра:

- 0 совпадений — контролируемая ошибка с доступными целевыми статусами; полезно вернуть для каждого `to.id`, `to.name`, а также `transition.id` и `transition.name`;
- больше 1 совпадения — контролируемая ошибка неоднозначности со всеми кандидатами;
- ровно 1 совпадение — выбран его `transition.id`.

Jira не гарантирует уникальность целевого статуса среди доступных переходов, поэтому нельзя молча брать первый элемент.

### 3. Проверить обязательные поля

Поля в `transition.fields` соответствуют transition screen. Официальный контракт отмечает обязательность через `required`; поля вне screen в метаданные не попадают. При отправке поля, отсутствующего в метаданных, Jira сообщает ошибку валидации. См. [Get transitions](https://docs.atlassian.com/software/jira/docs/api/REST/9.12.23/#api/2/issue-getTransitions) и [Do transition](https://docs.atlassian.com/software/jira/docs/api/REST/9.12.23/#api/2/issue-doTransition).

Для инструмента, который меняет только статус, безопасное правило: отклонить выбранный переход до записи, если хотя бы одно `transition.fields.*.required === true`. В ошибке перечислить `fieldId` (либо ключ объекта), `name`, `schema` и `hasDefaultValue`. Документация показывает `hasDefaultValue`, но не обещает, что одного этого признака достаточно для успешного пустого status-only запроса; ослаблять правило стоит только после отдельной проверки на целевом экземпляре Jira.

Workflow validators могут наложить дополнительные условия, не выраженные в `transition.fields`; окончательное решение всегда остаётся за `POST` Jira.

### 4. Выполнить переход

`POST /rest/api/2/issue/{issueIdOrKey}/transitions`

Минимальное тело для отдельного status-only инструмента:

```json
{
  "transition": {
    "id": "5"
  }
}
```

Нужно передавать id именно выбранного доступного перехода. `fields`, `update`, комментарий, resolution и прочие изменения не отправляются.

Документированные ответы:

- `204` — переход выполнен успешно; тела ответа нет;
- `400` — переход не указан;
- `404` — задача не существует либо пользователь не вправе её видеть;
- `500` — неверный transition id.

См. [Do transition](https://docs.atlassian.com/software/jira/docs/api/REST/9.12.23/#api/2/issue-doTransition) и схему `Issue Update` на той же странице.

Документация упоминает ошибки валидации полей, но не закрепляет для них отдельный статус и JSON-схему. Следовательно, клиент должен сохранять Jira error body через существующую нормализацию ошибок, не строя контракт на недокументированном конкретном коде.

### 5. Обязательно проверить результат

После `204` снова выполнить:

`GET /rest/api/2/issue/{issueIdOrKey}?fields=status`

Успех операции подтверждён только если фактический `fields.status.id` равен `transition.to.id`. Сравнение по id надёжнее имени; имя из повторного ответа следует использовать как `newStatus`.

Если повторное чтение не удалось или id не совпал, вернуть отдельную контролируемую ошибку проверки. В ней важно явно сообщить, что `POST` уже мог изменить задачу и слепой автоматический retry небезопасен.

## Рекомендуемый итоговый результат

```json
{
  "issueKey": "PROJ-123",
  "previousStatus": { "id": "1", "name": "Open" },
  "newStatus": { "id": "3", "name": "In Progress" },
  "transition": { "id": "5", "name": "Start Progress" },
  "changed": true
}
```

Для no-op `previousStatus` и `newStatus` одинаковы, `changed` равен `false`, а `transition` отсутствует либо `null`; это нужно однозначно закрепить в публичной Zod-схеме.

## Риски и границы контракта

- Между чтением переходов и `POST` состояние задачи или права пользователя могут измениться. Ответ `POST`, а затем повторное чтение являются авторитетными.
- Доступные статусы — это только назначения одношаговых переходов текущего пользователя, не полный справочник статусов и не многошаговый маршрут.
- Regистронезависимое сравнение и обрезка пробелов — логика MCP-инструмента, а не Jira REST API. Способ нормализации Unicode следует зафиксировать и тестировать отдельно.
- Успешный `204` не содержит обновлённую задачу, поэтому требуемый структурированный результат невозможно достоверно собрать без повторного `GET`.
