## Question

Какую наблюдаемую семантику задать обязательной проверке после POST, включая конкурентное изменение задачи и случай, когда переход уже выполнен, но повторное чтение завершилось ошибкой или вернуло неожиданный статус?

## Answer

Успешный изменяющий вызов требует двух наблюдений: Jira вернула `204` на POST выбранного перехода, а единственный обязательный проверочный GET затем вернул `fields.status.id`, равный `transition.to.id`. Имя и остальные данные `newStatus` берутся из проверочного ответа. Совпадение по id достаточно даже при отличающемся имени.

`changed: true` означает только сочетание подтверждённого Jira POST и наблюдавшегося при проверке целевого статуса. Оно не доказывает отсутствие конкурентных переходов между запросами, исключительную причинность инструмента или сохранение статуса после ответа.

Если первый GET уже показывает статус, имя которого после `trim()` совпадает с `targetStatus` без учёта регистра, этот же GET считается проверкой no-op. Инструмент сразу возвращает `changed: false`, одинаковые `previousStatus` и `newStatus`, а также `transition: null`; переходы и повторно задачу не читает, POST не выполняет.

`previousStatus` — статус, наблюдавшийся при первом GET. Он не гарантированно является состоянием непосредственно перед POST: Jira REST API не предоставляет атомарной операции сравнения статуса и выполнения перехода.

После `204` выполняется ровно один проверочный GET. Добавить два контролируемых кода:

- `TRANSITION_VERIFICATION_FAILED` — проверочный GET завершился контролируемой ошибкой, поэтому фактический статус неизвестен;
- `TRANSITION_STATUS_MISMATCH` — GET успешен, но фактический `status.id` отличается от ожидаемого.

Нормализованные детали ошибок:

```ts
// TRANSITION_VERIFICATION_FAILED
{
  issueKey: string,
  previousStatus: Status,
  expectedStatus: Status,
  transition: { id: string, name: string },
  causeCode: JiraErrorCode
}

// TRANSITION_STATUS_MISMATCH
{
  issueKey: string,
  previousStatus: Status,
  expectedStatus: Status,
  actualStatus: Status,
  transition: { id: string, name: string }
}
```

В них не публикуются HTTP-статус, URL, сырой ответ Jira или внутренняя причина. Несовпадение возвращается и тогда, когда фактический статус равен исходному, и тогда, когда конкурентный процесс уже перевёл задачу дальше.

Инструмент не делает автоматических retry, не перечитывает задачу для примирения после ошибки POST, не выбирает новый переход и не повторяет POST. Без доверенного `204` возвращается существующая нормализованная ошибка POST. При timeout или сетевой ошибке результат мутации может быть неизвестен; это ограничение явно документируется для потребителя. Любую последующую проверку или новый вызов инициирует потребитель после собственного подтверждения.
