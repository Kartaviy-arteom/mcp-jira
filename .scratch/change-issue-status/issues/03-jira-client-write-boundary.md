## Question

Какой минимальный write-контракт должен получить `jiraClient`, чтобы выполнить JSON POST с ожидаемым пустым ответом, сохранить действующие гарантии URL, авторизации, timeout и безопасных ошибок и не проектировать универсальный HTTP-клиент сверх нужд первой операции?

## Answer

Добавить в публичный интерфейс `jiraClient` один узкий метод:

```ts
postJsonNoContent({ pathname, query?, body, notFoundCode? }): Promise<void>
```

- `body` принимает JSON-совместимое значение; сериализация выполняется безопасно внутри клиента. Ошибка сериализации становится контролируемой ошибкой `BAD_REQUEST`, без утечки исходных данных.
- Клиент выставляет `Content-Type: application/json` и сохраняет `Accept: application/json`, Bearer-токен, запрет redirect, timeout, безопасную сборку URL и существующую классификацию HTTP-ошибок.
- Успехом считается только `204 No Content`. Любой другой `2xx` означает несовместимый ответ Jira и преобразуется в `RESPONSE_FORMAT_ERROR` с HTTP-статусом.
- Контекстный `notFoundCode` остаётся частью параметров; для перехода задачи вызывающий tool передаёт `ISSUE_NOT_FOUND`.
- Существующие публичные `getJson` и `getBinary` не меняются. Их общая механика `send`/`request` расширяется только внутри реализации параметрами HTTP-метода, тела и необходимых заголовков.
- Jira-специфичные сведения (`transition.id`, endpoint и выбор перехода) остаются в tool, а универсальный публичный `request` не добавляется.

Решение создаёт глубокий модуль: один дополнительный публичный метод скрывает сериализацию, транспортные гарантии и проверку пустого ответа. ADR не требуется — изменение локально и обратимо.
