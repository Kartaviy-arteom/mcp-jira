# 08: Добавить проверенную смену статуса задачи

**What to build:** добавить готовый для MCP-потребителя `change-issue-status`, который выполняет ровно один доступный workflow transition Jira по ключу задачи и имени целевого статуса, безопасно обрабатывает неоднозначность и обязательные поля и возвращает успех только после проверки фактического статуса.

**Blocked by:** 07: Подготовить безопасный write-контракт Jira-клиента.

**Status:** ready-for-agent

- [ ] Инструмент называется `change-issue-status`, имеет согласованное английское описание и автоматически обнаруживается по действующей convention инструментов.
- [ ] Строгий вход принимает только нормализуемый ключ задачи и непустое после `trim()` имя целевого статуса; невалидный ввод отклоняется до обращения к Jira.
- [ ] Публичный структурированный результат всегда содержит канонический ключ из первого чтения, исходный и новый статусы с id/name, nullable выполненный переход и `changed`.
- [ ] Инструмент объявляет `readOnlyHint: false`, `destructiveHint: true`, `idempotentHint: true` и `openWorldHint: true`; подтверждение мутации остаётся ответственностью MCP-потребителя.
- [ ] Первое чтение запрашивает только ключ и статус задачи через Jira REST API v2 и валидирует ответ Zod-схемой с контекстным `ISSUE_NOT_FOUND`.
- [ ] Если имя исходного статуса после обрезки пробелов совпадает с целью без учёта регистра, инструмент выполняет no-op: возвращает `changed: false`, одинаковые статусы и `transition: null`, не читая переходы и не выполняя другие запросы.
- [ ] Для изменения инструмент запрашивает доступные переходы с метаданными полей, валидирует ответ и сопоставляет целевой статус по тому же правилу нормализации.
- [ ] Ноль совпадений возвращает `TRANSITION_NOT_AVAILABLE` со всеми доступными переходами в исходном Jira-порядке; переходы с одинаковыми целевыми статусами не дедуплицируются.
- [ ] Несколько совпадений возвращают `TRANSITION_AMBIGUOUS` со всеми кандидатами и не выбирают переход произвольно.
- [ ] Единственный переход с любым `required: true` возвращает `TRANSITION_REQUIRES_FIELDS` с нормализованными transition/field details и не выполняет POST, включая случай `hasDefaultValue: true`.
- [ ] Единственный допустимый переход выполняется минимальным JSON POST только с его id; комментарий, resolution, assignee и другие поля не отправляются.
- [ ] Ошибка POST возвращается как существующая нормализованная Jira-ошибка без проверочного чтения, повторного выбора или retry.
- [ ] После доверенного `204` выполняется ровно одно повторное чтение статуса; автоматические retry и повторный POST отсутствуют.
- [ ] Ошибка проверочного чтения возвращает `TRANSITION_VERIFICATION_FAILED` с каноническим ключом, исходным/ожидаемым статусами, переходом и нормализованным `causeCode`, не раскрывая транспорт.
- [ ] Успешное чтение с неожиданным status id возвращает `TRANSITION_STATUS_MISMATCH` с ожидаемым и фактическим статусами независимо от причины гонки.
- [ ] Совпадение проверенного status id с целью возвращает `changed: true`; новый статус берётся из проверочного ответа, включая изменившееся имя при том же id.
- [ ] Все публичные результаты и локально сформированные error details проходят Zod-нормализацию; неизвестные Jira-поля и приватные fixture-данные наружу не попадают.
- [ ] Тесты через `toolCall` покрывают schema rejection, no-op, happy path, порядок запросов, нормализацию имён, отсутствие/неоднозначность перехода, обязательные поля, ошибки POST, оба проверочных исхода, конкурентные статусы, annotations и output schema.
- [ ] Тесты подтверждают, что `changed: true` означает только подтверждённый POST и наблюдаемый целевой status id, не обещая отсутствия последующих конкурентных изменений.
- [ ] Линтинг, проверка форматирования, строгая проверка типов, все тесты, TypeScript-компиляция и MCP build проходят успешно.
